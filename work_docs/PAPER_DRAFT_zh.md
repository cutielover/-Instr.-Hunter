# 一种微处理器隐藏指令分析工具的设计与实现

> 写作状态：中文初稿 v0.1  
> 说明：本稿基于当前已完成的 Layer A 与 Layer C 结果撰写；`§6.3` 与 `§6.4` 保留给后续实机实验补全。文中所有 `[待补]` 项均在拿到板卡后回填。

## 摘要

微处理器实现中可能存在规范未显式描述、工具链难以一致识别、或在不同执行环境下表现不一致的指令行为。此类行为不仅会影响处理器实现的正确性与可调试性，也会对系统软件验证、漏洞分析与第三方审计带来挑战。针对现有工作多聚焦单一 ISA、扩展成本高、以及容器/仿真与实机证据链分离的问题，本文设计并实现了一种面向 RISC 风格处理器的隐藏指令分析工具。该工具以用户态单条指令注入为核心，结合 `memcage` 与 `ptrace` 两类执行后端，通过信号、`si_code` 与反汇编结果联合完成异常行为分类；同时，本文引入配置驱动的后端生成链路，以降低新 ISA 的接入门槛。

在实现方面，本文完成了 RISC-V 与 AArch64 两个后端，并以 MIPS64 作为配置生成框架的首个案例，形成了从 `arch-spec` 到 `arch_*.c` 的可运行基线生成流程。在评估方面，本文首先在 Layer A 环境中验证了主循环稳定性与基础分类能力。实验表明，RISC-V `memcage` 短程扫描能够稳定完成并保留可审计日志；AArch64 `ptrace` 路径也能够稳定运行。在匹配子集上，AArch64 `memcage` 的 median 吞吐达到 `9362.29 insn/s`，高于 `ptrace` 的 `8192.00 insn/s`。同时，受控样例实验表明：当前系统已能稳定表达 legal 与 privileged-in-user 两类行为，但对 decoder-unknown illegal-at-test 与 known-disassembly exec-fault 两类路径仍存在 taxonomy / logging 缺口。对于扩展性，MIPS64 配置驱动生成链路已完成 quick smoke，表明“配置 + 生成 + 有界人工加固”的路线具备可行性。

本文当前阶段的主要局限在于：实机硅后验证尚未完成，因此关于实机可复现性与 Layer A / Layer B 差异归因的主张仍待补证。尽管如此，本文已经在 Layer A 与 Layer C 上形成了一套可扩展、可复现、可审计的分析框架与首批证据，并为后续真实硬件验证与多 ISA 扩展奠定了统一基础。

**关键词**：隐藏指令；指令空间扫描；`memcage`；`ptrace`；Capstone；代码生成；RISC-V；AArch64；MIPS

### 1.1 研究背景

随着处理器复杂度不断提升，指令行为与公开文档之间的不一致问题越来越难以完全依赖厂商文档或单一工具链发现。一方面，反汇编器给出的“可识别”结果并不等同于处理器一定接受该编码；另一方面，即使处理器能够执行某条编码，该行为也未必已经被官方手册、编译器或常见反汇编器完整描述。对于系统软件、漏洞挖掘、第三方验证与安全审计而言，这类“CPU 接受”和“工具链/文档认为合法”之间的偏差具有直接研究价值。

在已有工作中，x86 上的 `sandsifter` 通过大规模搜索和剪枝技术展示了隐藏指令发现的可行性；`iScanU` 则将类似思想扩展到 RISC 处理器，并强调了 `ptrace` 与 `memcage` 两条执行路径在用户态隐藏指令扫描中的价值。然而，现有方案仍存在三个不足。第一，多数工具更偏向特定 ISA 或单次研究型原型，缺少统一的多 ISA 扩展接口。第二，工具往往把“能跑起来”与“能较低成本接入新架构”视为两个彼此分离的问题。第三，仿真/容器环境与真实硬件之间的证据链在论文中常被分开描述，导致结果可信度与外推边界不够清晰。

### 1.2 研究问题

围绕上述不足，本文关注以下三个问题。

1. 如何在用户态环境中，以单条、可回收、可分类的方式对任意指令编码进行执行测试？
2. 如何以统一框架同时支持 `memcage` 与 `ptrace` 两类执行后端，并在多 ISA 场景下复用同一套编排逻辑？
3. 当新增一种 ISA 时，能否将 bring-up 过程从“完全手工重写后端”收敛为“配置 + 生成 + 有界人工加固”？

### 1.3 本文工作

针对上述问题，本文设计并实现了一种微处理器隐藏指令分析工具。该工具以 Python 编排层为外部入口，以共享的 `injector_core` 为执行核心，以 `arch_*` 后端承载具体 ISA 差异，并通过稳定的 raw/text 输出协议支持多 worker 扫描与离线分析。在执行控制方面，本文同时保留 `memcage` 与 `ptrace` 两类路径：前者更偏向高吞吐的用户态测试，后者更偏向可观察性与新架构 bring-up。为降低新 ISA 接入成本，本文进一步设计配置驱动的生成工具，以 `arch-specs/*` 为输入，自动产出可编译的架构后端基线与待人工检查清单。

### 1.4 主要贡献

本文的主要贡献如下。

1. 设计并实现了一套面向 RISC-V 与 AArch64 的用户态隐藏指令分析框架，统一了写指、执行、信号捕获、反汇编与分类主循环（第 4 章、第 5 章）。
2. 在统一框架中组织了 `memcage` 与 `ptrace` 两类执行后端，并通过匹配子集实验给出了两者在当前环境下的吞吐对比（第 4 章、第 6.2 节）。
3. 提出并实现了配置驱动的新架构生成链路，并以 MIPS64 作为首个案例验证“配置 + 生成 + 有界人工加固”的可行性（第 4.5 节、第 5.3 节、第 6.5 节）。
4. 采用 Layer A / B / C 的分层证据结构；当前已完成 Layer A 与 Layer C，Layer B 作为后续实机补证部分（第 6 章、第 7 章）。

### 1.5 论文结构

本文其余章节安排如下：第 2 章介绍相关工作与技术背景；第 3 章定义问题与设计目标；第 4 章给出系统总体架构与关键机制；第 5 章说明实现要点；第 6 章给出实验与评估；第 7 章总结全文并讨论局限与展望。

## 第 2 章 相关工作与技术基础

> `[表 2-1 待补]` `sandsifter`、`iScanU`、`armshaker` 与本文在目标 ISA、执行控制、ground truth、实机证据、扩展性上的对比。参见 `docs/FIGURE_TABLE_CHECKLIST_zh.md`。

### 2.1 隐藏指令与差异审计

隐藏指令研究并不应被狭义理解为“发现全新 undocumented opcode”。在第三方黑盒审计语境中，更广义的问题是：处理器真实执行行为、官方 ISA 规范、反汇编器结果以及仿真器表现之间是否存在可复现差异。因此，本文关注的不仅是狭义的 hidden instruction，也包括 disassembler mismatch、privileged-in-user、timeout 与执行期异常等行为分歧。

### 2.2 x86 方向工作

以 `sandsifter` 为代表的 x86 工作展示了隐藏指令挖掘的影响力，也提出了大量针对变长 ISA 的搜索空间剪枝思想。与之相比，本文并不试图复现 x86 的剪枝体系，而是聚焦固定字长或更容易统一构造测试页的 RISC 处理器，强调单条可控执行与多 ISA 统一扩展。

### 2.3 RISC 用户态扫描工作

`iScanU` 将用户态指令扫描推广到 RISC-V、ARMv8 等处理器，证明了 `ptrace` 与 `memcage` 的组合路线在 RISC 上同样有效。本文继承了其“写指-执行-信号-反汇编”这一基本思路，但在三个方面继续推进：一是使用更新的 Capstone 6 与 ISA 字符串驱动模式配置；二是将多 worker 编排与离线分析工具纳入统一工程结构；三是增加配置驱动生成器，把“可扩展 bring-up”本身纳入贡献叙事。

### 2.4 形式化语义、ground truth 与局限

反汇编器为大规模指令扫描提供了现实可用的 ISA 视图，但其本身并不是 authoritative semantics。若论文一方面讨论“decoder 与 CPU 可能不一致”，另一方面又完全把单一 decoder 当作真值来源，就会构成循环论证。因此，本文采用较保守的写法：Capstone 提供主要对照视图，第二解码器与人工复核用于 triage，实机验证则作为最终证据链的一部分，而不是由仿真环境直接替代。

与 Sail、合规测试框架以及 authoritative ISA semantics 相比，本文的定位并不是“证明处理器实现满足规范”，而是提供一种第三方可部署、面向黑盒处理器实现的差异审计工具。因此，本文更关注“可执行、可复现、可扩展”的工程方法，而不是形式化完备性。换言之，本文与形式化语义工作是互补关系，而不是替代关系。

### 2.5 Decoder / Emulator Disagreement

除处理器与规范之间的偏差外，decoder 与 emulator 自身也可能引入系统性差异。在本文实验中，RISC-V `--filter-ext` 与 raw/filtered hidden 双统计口径已经说明：同一编码集合在不同工具链视图下可能产生显著不同的“隐藏行为”计数。因此，本文后续所有结果解释都坚持一个原则：Layer A 结果首先是 triage 证据，而不是裸地被上升为硬件事实。

## 第 3 章 问题定义与设计目标

### 3.1 问题定义

给定一个目标 ISA、一个执行后端、一段待扫描编码空间以及当前运行环境，本文的目标是判定每条编码在“处理器执行结果”与“反汇编器合法性判断”之间是否存在行为分歧，并输出可复现、可审计的日志与元数据。

### 3.2 分类口径

本文使用如下工作分类：

- `H`：执行成功，但主反汇编器不认为其为合法指令；
- `D`：主反汇编器认为合法，但执行在测试指令处被处理器拒绝；
- `T`：执行超时；
- `X`：处理器接受后进入执行路径，但在执行期间触发其他异常；
- `P`：特权或权限相关行为；
- `UNKNOWN`：当前实验无法稳定归类，或仍需人工 triage。

需要说明的是，当前实现中的日志口径尚未完整覆盖上述每一类。例如，本轮受控实验已经暴露出：某些 illegal-at-test 与 known-disassembly exec-fault 路径不会自动进入 artifact 日志。因此，`P` 与 `UNKNOWN` 在当前阶段仍更多体现为论文写作与人工复核口径，而不是完全由系统自动输出的第一层标签。

表 3-1 给出当前工作分类与“日志是否自动输出”的对应关系。

| 标签 | 含义 | 当前日志自动输出 | 当前已知缺口 |
|------|------|------------------|--------------|
| `H` | 执行成功，但主反汇编器不认为合法 | 部分是 | RISC-V 有 raw/filter 口径；AArch64 当前样例未覆盖到稳定 `H` |
| `D` | 主反汇编器认为合法，但执行在测试指令处被拒绝 | 是 | AArch64 privileged-in-user 当前折叠在 `D(strict)` 中 |
| `T` | 执行超时 | 是 | 仅代表当前 watchdog/timeout 口径下的超时 |
| `X` | 执行期间触发其他异常 | 部分是 | 已知 disassembly-known exec-fault/trap 路径当前未稳定进入 artifact |
| `P` | 特权或权限相关行为 | 否 | 当前更多依赖人工 triage，而非独立自动标签 |
| `UNKNOWN` | 当前无法稳定归类 | 否 | 需结合第二解码器与人工复核产生 |

### 3.3 设计目标

本文系统设计围绕以下目标展开：

1. 单条可控执行；
2. 运行后 harness 仍可回收并持续扫描；
3. 用户态可部署；
4. 多 ISA 共用同一编排骨架；
5. 新 ISA 接入成本可量化；
6. 仿真/容器结果未来能够与实机结果对照。

### 4.1 总体架构

系统由三部分组成。第一部分是 Python 编排层，负责参数解析、worker 管理、结果汇总与离线分析入口。第二部分是共享执行核心 `injector_core`，负责调度当前 ISA 后端、写入测试指令、触发执行并将结果输出为统一格式。第三部分是 `arch_riscv.c`、`arch_aarch64.c` 与 `arch_mips.c` 等架构后端，用于封装不同 ISA 在指令大小、信号语义、黑名单规则、寄存器沙箱和跳板实现上的差异。

### 4.2 扫描主循环

一次扫描的基本流程如下：首先在测试页写入待测编码，并在其后布置哨兵指令；随后转移执行流至测试页首；若执行过程中触发异常，则由信号处理逻辑记录 `signum`、`si_code` 与故障地址；之后调用 Capstone 对该编码进行反汇编；最后基于“执行结果 + 反汇编结果”联合完成分类，并写入同步文件与最终日志。

从工程组织上看，这一主循环被拆成两层。第一层是 Python 编排层，负责命令行参数、ISA 检测、worker 分片与收尾落盘；第二层是 C 侧执行器，负责真正的“写指-执行-捕获-返回”。这种拆分有两个直接收益。其一，不同 ISA 的差异主要被限制在 `arch_*` 后端内部，而不必扩散到整个前端控制逻辑。其二，Python 层可以在不理解所有微观执行细节的前提下，对多个 worker 的 raw 帧进行统一解析和聚合。

当前实现同时支持 text 与 raw 两种输出协议。text 输出便于人工检查和日志归档，而 raw 输出面向 `sifter.py` 的 reader 线程，能够用固定长度帧传递 `worker_id`、`disas_known`、`disas_illegal`、`encoding`、`signum` 与 `sicode` 等信息。相比完全用文本管道通信，raw 协议减少了解析歧义，也降低了多 worker 并行时的字符串处理开销。

### 4.3 `memcage` 路径

`memcage` 的核心思想是在用户态构造受限执行环境：测试页用于注入待测指令，陷阱页和 guard page 用于吸收大多数寄存器跳转与越界访问；超时机制负责收回死循环或等待型指令。该路径的优势在于吞吐更高，但对不同 ISA 的寄存器沙箱、哨兵语义与信号细节依赖也更强，因此很难完全配置化。

具体而言，`memcage` 至少依赖以下几类 ISA 特定设计。第一，哨兵指令必须选择一种既能稳定产生可识别后继行为、又不会与常见测试指令语义过度冲突的编码。第二，寄存器沙箱需要把大多数通用寄存器预置到“陷阱安全地址”，以降低寄存器跳转、访存或错误返回路径对 harness 的破坏。第三，信号处理逻辑必须结合 `si_addr` 或等价上下文，区分“测试指令本身被拒绝”和“测试指令执行成功后命中哨兵”这两种情况。也正因为这三类设计都高度依赖 ISA 语义，本文将 `memcage` 明确视为“高吞吐但高特化”的后端。

从 alternatives 的角度看，本文并未选择“完全由 `ptrace` 替代 `memcage`”，原因在于两者解决的是不同问题。`ptrace` 的确更有利于 bring-up 与调试，但当扫描子空间扩大时，其 stop/resume 和系统调用开销会迅速累积；相反，`memcage` 可以在用户态内维持较低的单条指令切换开销。因此，本文选择保留 `memcage`，同时在写作中诚实承认它的 ISA 特化程度更高。

### 4.4 `ptrace` 路径

`ptrace` 路径通过 tracer/tracee 模式对单条指令进行更强的可观察控制。与 `memcage` 相比，它在调试、bring-up 与新 ISA 接入时更稳健，但代价是系统调用与 stop/resume 带来的额外开销。本文将其视为“通用性更强、性能通常较低”的互补后端。

在架构设计上，`ptrace` 路径更接近一种“最小可移植后端”。对于新 ISA 来说，只要能够给出基本的寄存器读写、程序计数器定位、测试页写入以及单步执行接口，就可以较快得到一个可运行原型。也正因如此，本文在扩展性叙事中把 `ptrace` 视为更友好的默认 bring-up 路径，而把 `memcage` 视为在其之上的性能与安全强化层。换言之，生成器的目标并不是一步到位地产出高质量 `memcage`，而是优先产出一个可以接入统一编排框架的基线后端。

### 4.5 配置驱动生成链路

为降低新 ISA bring-up 成本，本文设计了配置驱动的后端生成器。其输入为 ISA 描述文件，例如 `arch-specs/mips64el.json`；生成器根据配置产出 `src/arch_mips.c` 这一可编译基线，以及 `src/arch_mips.c.MEMCAGE_TODO.md` 这一人工检查清单。该设计的重点不在于宣称“零人工支持新 ISA”，而在于明确区分：哪些部分可以由配置安全推导，哪些部分仍需要架构特定的人工加固。

在当前实现中，可由配置直接描述的内容包括：Capstone 架构与模式宏、指令固定长度、基础黑名单、哨兵指令、寄存器组结构、`ptrace` 所需的 PC/GPR 字段名等。相比之下，寄存器沙箱策略、异常语义与 `si_addr` 解释、以及特权/缓存/TLB 敏感指令的黑名单收敛，则更适合以 `MEMCAGE_TODO` 的方式显式暴露给开发者。这样的分工虽然保守，但避免了在缺少足够语义保证时，由生成器“自信地”输出错误的架构假设。

### 4.6 多 worker 分片与结果聚合

除执行路径外，本文系统设计的另一个关键点是多 worker 分片。在 exhaustive 且 `-j N > 1` 时，Python 前端会把编码空间划分成多个 shard，每个 worker 启动独立执行器处理自己的子区间。这样的设计使得并发扩展不需要共享复杂状态，同时也方便在 `run.json` 中记录每个 worker 的最后编码、崩溃次数与局部统计。

与“单进程内部多线程扫描”相比，独立进程 + 独立 reader 线程的架构更有利于故障隔离。即使某个 worker 异常退出，前端也能够根据 `last_encoding` 与分片边界恢复局部进度，而不必整体中止所有扫描任务。虽然本文当前实验还没有把 restart 机制当作主要贡献展开，但从工程上看，这一设计为后续更大规模扫描保留了必要的稳定性基础。

## 第 5 章 实现

### 5.1 RISC-V 与 AArch64 后端

当前系统已完成 RISC-V 与 AArch64 两个主后端实现。RISC-V 后端支持压缩指令、ISA 字符串驱动的 Capstone `cs_mode` 配置，以及面向扩展过滤的 `--filter-ext` 逻辑。AArch64 后端则采用更严格的 `D(strict)` 口径，以减少用户态不可执行编码带来的噪声。

在 RISC-V 路径上，当前实现已经把“Capstone 可解码但 ISA 非法”与“Capstone 完全不识别”这两类情况区分开来，并通过 `/proc/cpuinfo` 中的 ISA 字符串选择更贴近当前执行环境的 `cs_mode`。此外，为缓解扩展相关假阳性，系统在启用 `--filter-ext` 时会同时保留 `raw_hidden_count`、过滤后 `hidden_count`、以及按扩展分组的 `filtered_hidden_ext_counts`。这使得同一轮实验既能保留 raw H，也能给出更适合 Layer A triage 的过滤后口径。

在 AArch64 路径上，当前实现更强调“严格 mismatch”而不是“宽松 anomaly tally”。这也是为什么 `D(strict)` 会被单独保留为主要日志口径：对于大量用户态不可执行但反汇编器能识别的编码，如果不加约束地全部计入“异常”，实验会被噪声主导。因此，本文当前 AArch64 结果首先是一组稳定的对照基线，而不是“发现了大量隐藏行为”的证据。

### 5.2 结果落盘与离线分析

系统在运行过程中维护 `sync` 文件以供实时观察，并在收尾阶段生成 `data/log` 与 `run.json`。本轮工作中，RISC-V 路径已增加 `raw_hidden_count`、`hidden_count`、`filtered_hidden_count` 与 `filtered_hidden_ext_counts` 等统计字段，使同一次实验即可同时保留 raw H 与过滤后 H 的信息。

从论文证据角度看，`data/log` 与 `run.json` 具有不同角色。前者更适合作为实验章节中的主结果来源，因为它直接体现了测试条数、异常计数与代表性 artifact；后者则更适合作为可复现元数据，补充记录命令行、worker 分片、运行时长、过滤选项与当前后端配置。为了避免只保留“最终计数”而丢失解释上下文，本文还额外冻结了 artifact bundle schema 与 second decoder wrapper，用于支撑后续人工 triage。

当前项目的离线分析由 `summarize.py` 与 `analysis/` 辅助脚本承担。它们负责对最终日志进行家族聚合、样本展示和 CSV 导出。本文将这些工具纳入实现章节，而不是放在附录中略过，原因在于：对于一篇强调“可审计”和“可扩展”的论文来说，扫描后的解释链路与扫描本身同样重要。

### 5.3 MIPS 生成器案例

MIPS64 是本文当前的首个生成器案例。配置文件 `arch-specs/mips64el.json` 仅 36 行，却能够驱动生成器产出 497 行的 `src/arch_mips.c` 基线实现，并自动生成包含 3 条人工检查项的 `MEMCAGE_TODO` 文档。实验表明，该生成结果已经能够在容器环境中完成 quick smoke，从而证明“配置 + 生成 + 有界人工加固”并非仅停留在设计层面。

更重要的是，MIPS 案例把“自动化能做什么”和“自动化不能做什么”具体化了。自动化已经能够生成基础哨兵、黑名单与统一接口骨架，使新后端可以进入同一套编排和构建链路；但寄存器沙箱、BREAK 哨兵在原生 Linux/MIPS64 上的行为、以及 cache/TLB 敏感指令的黑名单调优，仍必须显式外露。这种“自动生成基线 + TODO 驱动人工加固”的产物形态，本身就是本文对“可扩展性”给出的工程回答。

### 5.4 当前实现边界

在当前稿中，有三条实现边界需要明确写出。第一，本文尚未把分类输出扩展成完整的 `H/D/P/T/X/UNKNOWN` 自动标注系统；尤其在 AArch64 controlled illegal 与 trap 路径上，日志口径仍有缺失。第二，本文当前所有吞吐结果都来自 Layer A，而不是实机环境。第三，生成器产出的 MIPS 后端虽然已可运行，但还不能与已经成熟的 RISC-V、AArch64 后端划等号。将这些边界写在实现章而不是只放在结论里，有助于降低读者对正文主张的误解。

### 6.1 Layer A：稳定性与受控样例

本节对应 `C1` 与收缩版 `C4`。核心问题不是“我们是否已经发现新的硬件隐藏指令”，而是“当前框架在受控 Layer A 环境中是否稳定、可审计，并能否通过小规模样例验证分类链路的关键路径”。

首先，本文在 Layer A 环境中完成了主循环稳定性检查。RISC-V `memcage` 的两组短程扫描 `R001` 与 `R002` 均能够稳定完成并生成完整日志；AArch64 `ptrace` 的短程 sanity `R003` 也能够稳定收尾并产生一致结果。这说明，在声明的 Linux 容器环境下，当前框架已经具备基本可重复性。

表 6-1 总结了当前 Layer A 稳定性与受控样例实验。

| Run ID | 平台/后端 | 子集/样例 | 主要结果 | 对应主张 |
|--------|-----------|-----------|----------|----------|
| `R001` | RISC-V `memcage` | `0x00000000-0x00000fff` | `Tested=4064`，`Raw H=31`，`H=0`，`D=97`，`T=33`，`X=32` | 主循环可稳定运行并落盘 |
| `R002` | RISC-V `memcage` | `0x00010000-0x00010fff` | `Tested=992`，worker crash count 全零 | containment 与基础稳定性 |
| `R003` | AArch64 `ptrace` | `0x00000000-0x0000ffff` | `Tested=65536`，`D(strict)=65536` | ptrace 路径稳定可跑 |
| `R004` | AArch64 `ptrace` | legal case | 无异常 artifact | 受控 legal 路径 |
| `R005` | AArch64 `ptrace` | illegal case | 运行结束但无 artifact | 暴露 taxonomy/logging gap |
| `R006` | AArch64 `ptrace` | privileged case | `D(strict)=1` | privileged-in-user 当前折叠到 `D` |
| `R007` | AArch64 `ptrace` | trap candidates | 运行结束但无 artifact | 暴露 exec-fault/trap logging gap |

其次，本文对 AArch64 `ptrace` 路径执行了 4 组受控单样例实验。

1. `R004`：合法样例 `mov x0, #1`，结果未出现任何 `H/D/X/T` artifact，符合预期。
2. `R005`：非法样例 `.inst 0xffffffff`，实验能够稳定结束，但当前分类器未显式输出 artifact，表明“decoder-unknown illegal-at-test”路径尚未进入现有日志 taxonomy。
3. `R006`：特权样例 `mrs x0, CurrentEL`，实验稳定记录为 `D(strict)=1`。这说明当前系统能够稳定暴露该类行为，但尚未把它从 `D` 中剥离成独立的 `P`。
4. `R007`：两组 memory-trap candidate 均能稳定执行结束，但当前日志仍未暴露相应 artifact，表明“known-disassembly exec-fault”路径尚未进入当前自动分类输出。

因此，本文当前更稳妥的表述不是“分类器已完整覆盖 H/D/P/T/X”，而是“当前系统已能稳定表达 legal 与 privileged-in-user 两类受控路径，并通过 illegal/trap 样例发现了 taxonomy / logging gap”。这一结果既是局限，也是对后续系统完善的直接指引。

### 6.2 Layer A：后端吞吐对比

本节对应收缩版 `C2`。目标不是证明 `memcage` 在所有环境下都优于 `ptrace`，而是在一个严格对齐的工作负载上比较两者的吞吐表现，并观察在 coverage 一致时是否仍存在稳定差异。

为比较 `memcage` 与 `ptrace` 的性能差异，本文在 AArch64 上选取了相同的扫描子空间 `0x00000000-0x0003ffff`，固定 `-j 10`，分别执行 3 次 `memcage` 与 3 次 `ptrace` 重复实验。当前结果仅适用于这一匹配子集及其对应 Layer A 环境。终稿中还需在表格中补齐镜像标识、宿主环境、内核与编译版本。两组实验的 coverage 完全一致：每次均测试 `262144` 条编码，且都记录到 `65536` 条 `D(strict)`，未出现 `H`。

实验结果如下。

| 后端 | 重复次数 | 扫描范围 | Tested | median 吞吐（insn/s） | 备注 |
|------|----------|----------|--------|------------------------|------|
| `memcage` | 3 | `0x00000000-0x0003ffff` | `262144` | `9362.29` | 三次结果分别约为 `8456.26`、`9362.29`、`9362.29` |
| `ptrace` | 3 | 同上 | `262144` | `8192.00` | 三次结果分别约为 `7489.83`、`8192.00`、`8456.26` |

从当前 matched subset 看，`memcage` 的 median 吞吐约比 `ptrace` 高 `14.3%`。不过，本文不将这一结果夸大为“普遍显著领先”，因为该结论目前仅建立在 AArch64 的一个对齐子空间之上，且两边产出的 artifact 分布高度一致、均以 `D(strict)` 为主。更合理的写法是：在当前 Layer A matched subset 上，`memcage` 表现出稳定但有限的吞吐优势。

这一结果还带来一个重要的写作收益：由于 R008 与 R009 的 coverage 一致，本文可以把 throughput 对比写成一种“相同工作、不同后端”的系统实验，而不是“不同异常分布下的不可比 benchmark”。对系统论文而言，这样的对齐实验往往比单纯的更高吞吐数字更重要。

### 6.5 Layer C：生成器案例研究

本节对应收缩版 `C7`。其关注点不是“生成器能否立即替代所有人工实现”，而是“它是否已经把 bring-up 从零开始编码，转化为配置驱动的可运行基线生成问题”。

在扩展性验证方面，本文已完成 MIPS64 生成器 quick smoke。实验命令为 `./scripts/macos-docker-run-mips64.sh quick`，墙钟时间约 `16.27s`。该结果说明：在当前工程结构下，MIPS64 已不再需要从零手写完整后端，而是可以通过配置文件与生成器快速得到一个可运行基线。

不过，该结果并不意味着 MIPS64 已达到与 RISC-V、AArch64 同等级的成熟度。根据自动生成的 `src/arch_mips.c.MEMCAGE_TODO.md`，当前仍至少存在以下 3 项人工工作：寄存器沙箱语义检查、BREAK 哨兵语义与 `si_addr` 行为确认，以及面向真实硬件的黑名单调优。因此，生成器贡献应被写成“显著降低 bring-up 成本”，而非“完全自动化支持新 ISA”。

表 6-3 给出当前 Layer C 案例的最小量化信息。

| 项目 | 当前值 | 含义 |
|------|--------|------|
| 配置文件行数 | `36` | MIPS64 规格输入规模 |
| 生成后端行数 | `497` | 自动生成的 `src/arch_mips.c` |
| 人工检查项 | `3` | `MEMCAGE_TODO` 中尚未关闭的条目 |
| quick smoke 时间 | `16.27s` | 从调用脚本到得到可运行结果的墙钟时间 |

因此，当前 Layer C 最稳妥的结论是：本文已经证明“生成器能将新 ISA 接入问题压缩为一个小规格输入 + 一个可运行基线 + 一个显式人工检查清单”，而不是证明“生成器已经完全替代人工 ISA 工程”。

## 第 7 章 讨论与局限

首先，本文当前仍以反汇编器作为主要 ISA 视图。尽管这在工程上是现实可行的，但它并不等同于 authoritative semantics，因此所有 decoder-related 结论都必须结合第二解码器、人工 triage 与后续实机验证理解。

其次，本文受控样例实验已经显示：当前自动分类输出并未完整覆盖所有理论上希望表达的路径。特别是 illegal-at-test 与 known-disassembly exec-fault 两类样例虽然已经通过实验显式暴露出来，但尚未稳定进入 artifact 日志。相比于回避这一点，本文选择将其作为系统局限诚实报告。

再次，本文目前尚未完成真实硬件实验。因此，任何关于“硬件可复现性”和“Layer A / Layer B 差异可解释性”的结论都必须推迟到后续板卡实验后再写入最终定稿。

最后，生成器虽然降低了新 ISA 接入门槛，但 `memcage` 的高质量实现仍然依赖架构特定 hardening。配置生成在当前阶段更适合被理解为“生成可运行基线”，而不是完全替代 ISA 工程。

## 第 8 章 总结与展望

本文设计并实现了一种微处理器隐藏指令分析工具，围绕单条可控执行、多 ISA 共用编排、双后端互补与配置驱动扩展四条主线展开。当前系统已经在 RISC-V 与 AArch64 上完成主链路实现，并通过 Layer A 实验验证了主循环稳定性、匹配子集吞吐对比以及部分受控样例路径；同时，以 MIPS64 为例验证了“配置 + 生成 + 有界人工加固”的扩展路线。

在当前已获得的结果基础上，本文已经能够支持一篇以系统设计、Layer A 评估与扩展性案例为主体的中文论文初稿。但若要形成完整闭环，后续仍必须完成 RISC-V 实机复现实验，并据此补全 Layer A / Layer B 对照与最终结论。

未来工作将从三个方向继续推进：其一，补齐真实硬件实验与差异归因；其二，完善当前 taxonomy / logging gap，使更多受控路径能够直接进入自动化分类输出；其三，将配置生成器推广到更多 ISA，并探索与形式化 ISA 语义或合规测试框架的结合。
